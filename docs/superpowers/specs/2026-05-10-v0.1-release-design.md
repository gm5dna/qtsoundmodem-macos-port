# mac-0.1.0 Release Design

**Date:** 2026-05-10
**Author:** Stuart (gm5dna), with Claude
**Status:** Draft, pending review

## Goal

Cut the first tagged release of the QtSoundModem macOS port, publish it as a GitHub Release with built artefacts and checksums, and commit a CHANGELOG that summarises the fork's delta from upstream.

## Scope

### In scope
- New `CHANGELOG.md` at repo root, Keep-a-Changelog format, single section `[mac-0.1.0] – 2026-05-10`.
- New `.github/workflows/release.yml` that builds `.app` → `.dmg` on `macos-14` and publishes a GitHub Release when a `mac-*` tag is pushed.
- Helper script (e.g. `scripts/extract-release-notes.sh`) to slice the changelog section for a tag into the GitHub Release body.
- Tagging `macos-port` HEAD as `mac-0.1.0` and publishing the Release with `.dmg` and `SHA256SUMS`.
- README pointer to the changelog.

### Out of scope
- Bumping the `gm5dna/homebrew-amateur-radio` formula. Tap continues to track `macos-port` HEAD.
- Universal binary (x86_64 + arm64). v0.1 is arm64-only.
- Developer ID signing / notarisation. Ad-hoc only; release notes explain Gatekeeper steps.
- Merging `tooltips` into `macos-port`. Stays outside v0.1.
  Note: `feature/rx-offset-ux` is *already* in `macos-port` history (tip `55b56f9` is an ancestor of HEAD), so its work ships with v0.1 and must appear in the changelog.
- Backfilling changelog entries for pre-fork upstream history.
- Continuous integration for ordinary commits. The workflow only runs on `mac-*` tag pushes.
- Retroactively rewriting README sections that overlap with changelog content beyond a one-line pointer.

## Versioning

**Scheme:** `mac-MAJOR.MINOR.PATCH`, applied as a git tag.

**First tag:** `mac-0.1.0` on the tip of `macos-port` at the moment of execution (currently commit `629ec74`, "README: trim and reframe as personal, AI-assisted port"). Exact commit confirmed at tag-creation time.

**Rationale:**
- `mac-` prefix discriminates this fork's tags from upstream's `0.64`–`0.76` and `24.45` namespace; no collision risk if upstream resumes a `0.x` line.
- Three-part semver-style suffix keeps tooling (Homebrew, brew-readable tap formulas, `gh`) happy.
- `mac-0.1.0` signals "first usable cut of the port" rather than "feature-complete".

**Future tags:** `mac-0.1.1` for patches against this release; `mac-0.2.0` once meaningful new work lands (e.g. once one or more of the parked feature branches merge).

```
[mac-0.1.0]: https://github.com/gm5dna/qtsoundmodem-macos-port/releases/tag/mac-0.1.0
```

### Curation
- Source: `git log master..macos-port` (81 commits as of 2026-05-10).
- One bullet per coherent change, not one per commit. Bullets are user-facing where possible.
- Each fix that also affects upstream is flagged as such, since they are candidate upstream patches:
  - Buffer overflow in AGW frame monitor on long IL2P frames (`45ddc4e`).
  - PTT On/Off String hex-only parse trap (`99716e3`).
  - AGW TX / port-list raw channel index alignment (`5359076`).
- README sections that overlap with the changelog get a one-line pointer ("See CHANGELOG.md for the full delta from upstream"); no other README edits.

## Release workflow (`.github/workflows/release.yml`)

### Trigger
```yaml
on:
  push:
    tags:
      - 'mac-*'
```
Workflow fires only on release tags; never on ordinary commits.

### Runner
`macos-14` (Apple Silicon, GA). arm64-only build for v0.1.

### Job permissions and auth
```yaml
permissions:
  contents: write   # required for gh release create
env:
  GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

### Tag-driven variables
The workflow derives a single `VERSION` from `$GITHUB_REF_NAME` (e.g. `mac-0.1.0` or `mac-0.0.0-rc1`) and uses it for the artefact filename, the changelog lookup, and the release title. No version string is hard-coded in the workflow or helper script.

```yaml
env:
  VERSION: ${{ github.ref_name }}    # e.g. mac-0.1.0
  DMG_NAME: QtSoundModem-${{ github.ref_name }}.dmg
```

### Job steps (sketch)
1. `actions/checkout@v4` with `fetch-depth: 0`.
2. Install dependencies: `brew install qt@6 fftw hidapi`.
3. CMake configure: `-DCMAKE_BUILD_TYPE=Release -DCMAKE_OSX_DEPLOYMENT_TARGET=14.0`.
4. `cmake --build build`.
5. `macdeployqt build/QtSoundModem.app` to bundle Qt frameworks.
6. Ad-hoc codesign the bundle: `codesign --deep --force --sign - QtSoundModem.app`.
   Operate inside `$TMPDIR` to avoid the file-provider / FinderInfo re-stamp trap.
7. Wrap in a `.dmg` via `hdiutil create` (or `create-dmg` if layout matters — to be settled during plan execution). Output filename `${DMG_NAME}`.
8. Compute checksums: `shasum -a 256 "$DMG_NAME" > SHA256SUMS`.
9. Extract release notes for `$VERSION` from `CHANGELOG.md` via helper script. If no matching section exists (e.g. on an rc tag before changelog landing), fall back to the `[Unreleased]` block plus a "release candidate — not for production" header, so the rc dry-run still produces a sensible Release body.
10. `gh release create "$VERSION" --notes-file release-notes.md "$DMG_NAME" SHA256SUMS`. Pre-release flag set automatically when `$VERSION` contains `-rc`.

### Release body
- Top: the `mac-0.1.0` section extracted from `CHANGELOG.md`.
- Fixed footer:
  - Gatekeeper bypass instructions for ad-hoc-signed `.dmg` (`xattr -d com.apple.quarantine /Applications/QtSoundModem.app` and right-click → Open).
  - `shasum -a 256 -c SHA256SUMS` verification command.
  - Pointer to the Homebrew tap as the preferred install route.
  - Link to README and CHANGELOG.

### Known interaction risks
- `macdeployqt` may overlap with CMake's existing FFTW bundling (`bbe9e16`). Sanity-check before relying on both.
- `macos-14` runner brew formulae drift; if a runner-image bump breaks the build, switch to a `brew bundle` lockfile then.
- Ad-hoc-signed `.dmg` always trips Gatekeeper on first launch. Release notes must be unambiguous enough for a non-technical user.

## Execution sequence

1. Switch to `macos-port`; clean tree; `git pull --ff-only`.
2. Draft `CHANGELOG.md` and the README pointer line. Leave uncommitted.
3. **Review gate A:** `codex review --uncommitted` on the changelog and README diff. Fold notes back in. Second pass by Claude. Commit when both reviewers are satisfied.
4. Draft `.github/workflows/release.yml` and `scripts/extract-release-notes.sh`. Leave uncommitted.
5. **Review gate B:** `codex review --uncommitted` on the workflow and helper. Fold notes back in. Commit when satisfied.
6. Push `macos-port` to `origin`.
7. Dry run: push a throwaway `mac-0.0.0-rc1` tag, watch the workflow, verify the `.dmg` opens locally and the Gatekeeper instructions work for a fresh download. Delete the rc tag and rc release.
8. Tag `mac-0.1.0` on the agreed commit; push the tag. Workflow publishes the Release with `.dmg` + `SHA256SUMS`.
9. Post-publish verification: download the `.dmg` fresh, check SHA-256, open the app.

## Two-reviewer discipline

Per the project workflow memory, every non-trivial commit on this work pairs:
- `codex review --uncommitted` (CLI; not the subagent), and
- a separate read by Claude.

The spec itself goes through `codex review --uncommitted` before user review (see "Spec review" below).

## Rollback

- Bug found pre-publish (dry-run stage): delete rc tag and release, fix, re-dry-run.
- Bug found post-publish, minor: ship `mac-0.1.1` with the fix.
- Bug found post-publish, severe: `gh release delete mac-0.1.0` and `git push --delete origin mac-0.1.0` for an atomic do-over; then re-tag once fixed. Note: this breaks any link already shared, so use only for genuinely broken artefacts.

## Spec review

Before user review, this spec is read by `codex review --uncommitted` (uncommitted = changes since last commit on the working branch). Notes folded back inline. User then reviews the final document.

### Codex review 1 — 2026-05-10
Three P2 findings, all accepted and folded in:
1. `feature/rx-offset-ux` was wrongly listed as out of scope — its tip is already in `macos-port` history; corrected.
2. Workflow hard-coded the v0.1 DMG name and assumed a matching CHANGELOG section, breaking rc dry-runs and future tags; replaced with `$VERSION`-driven artefact name and a fallback for missing changelog sections.
3. Workflow lacked `GH_TOKEN` env and `contents: write` permission; added explicitly.

## Open questions for the user

- Confirm tag commit at execution time (`macos-port` HEAD may advance between now and the tag).
- Decide `hdiutil create` vs `create-dmg` once the workflow draft is in front of you.
- Decide whether the README pointer is a separate commit or part of the CHANGELOG commit.
